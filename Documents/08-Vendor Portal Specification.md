Vendor Portal Software Specification

1. Overview

The Vendor Portal is a lightweight, read-only web interface that allows the vendor to view customer order details after an order has been confirmed by the Admin.

The Vendor Portal is not intended to be a complete dashboard.

Its sole purpose is to allow the vendor to retrieve shipping information and dispatch the ordered products.

The portal must be simple, fast, secure, and mobile-friendly because the vendor will most likely access it from a smartphone.

2. Objectives

The Vendor Portal should:

Eliminate manual copying of customer information.
Reduce shipping mistakes.
Standardize communication.
Provide only the information required to dispatch an order.
Prevent unauthorized access.
Require no login or account creation. 3. Authentication

The Vendor Portal does not use usernames or passwords.

Instead, every confirmed order receives a unique Vendor Access Token generated by the backend.

Example:

https://alameencollective.com/vendor/4Jks9LxPQ8mV1YbR

The token must:

Be cryptographically secure.
Be impossible to guess.
Be unique.
Be generated only after an order is confirmed. 4. Access Flow

The Vendor Portal must be completely read-only.

The vendor must not be able to:

Edit products.
Edit customer details.
Change quantities.
Confirm orders.
Cancel orders.
Delete orders.
Modify pricing.

No forms should be displayed.

11. Invalid Access

If the token is invalid:

Display:

Order not found.

Please contact Al Ameen Collective if you believe this is an error.

If the token has been revoked:

Display:

This vendor link is no longer valid.

Please contact Al Ameen Collective.

If the order has been cancelled:

Display:

This order has been cancelled.

No shipment is required. 12. Security

The Vendor Portal must:

Validate the token on every request.
Never expose database IDs.
Never reveal internal system information.
Prevent URL enumeration attacks.
Use HTTPS in production.
Prevent caching of sensitive order information where appropriate.
Log vendor link access for audit purposes. 13. Responsive Design

The Vendor Portal should be optimized for:

Mobile phones (primary target)
Tablets
Desktop browsers

Cards should stack vertically on small screens.

Buttons (if any future actions are added) should be touch-friendly.

14. Future Expansion

The portal should be designed to support future enhancements without changing the architecture.

Possible future features include:

Vendor login and authentication.
Multiple vendors.
Shipment status updates.
Courier tracking numbers.
Dispatch confirmation.
Shipping labels.
Invoice generation.
Downloadable packing slips.
Dispatch history.

These features are out of scope for Version 1 but should be accommodated by the architecture.

15. UI Guidelines

The Vendor Portal should use the same design language as the customer website but with a simplified layout.

Use:

The same typography.
The same color palette.
The same button styles (if needed).
The same spacing system.

The interface should prioritize readability over visual richness.

16. Performance

The Vendor Portal should:

Load in under two seconds on a standard mobile connection.
Fetch only the data required for the displayed order.
Avoid unnecessary JavaScript or animations.
Display loading skeletons while retrieving order information. 17. AI Development Constraints

The AI development agent must:

Build the Vendor Portal as a standalone public route (/vendor/:token).
Treat the vendor token as the sole means of authorization.
Render only read-only information.
Prevent modification of any order data.
Follow the same design system defined in the UI/UX Specification.
Consume data exclusively through backend APIs.
Keep the implementation modular to allow future vendor features.
⭐ One Architectural Improvement

I recommend not storing the vendor token directly in the orders table.

Instead, create a separate table called vendor_access_tokens:

Column Purpose
id UUID
order_id Foreign key to the order
token Secure random token
is_active Whether the link is valid
expires_at Optional expiration timestamp
created_at Creation time
last_accessed_at Last time the vendor opened the link

This approach has several advantages:

You can revoke and regenerate links without modifying the order.
You can track when a vendor accessed an order.
You can support multiple active links if your business grows to multiple vendors.
It keeps authentication data separate from business data, which is a cleaner architectural design.
